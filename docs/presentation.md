## Assignment Context

I was assigned the task of researching and developing a sample project for API Connector Integrations within the DataFuseAI platform.

DataFuseAI is an ETL operations platform that already supports a range of data source connectors — relational databases (RDBMS), NoSQL databases, cloud object storage (S3, AWS, Azure), and file uploads. What was missing was support for APIs. This project is the POC: a standalone implementation, built separately from the main platform, that demonstrates how to connect to various APIs across multiple authentication methods and pagination strategies, and how to extract, infer, and preview data from those APIs in a structured, reliable way.

## Background — Where Data Lives and Why APIs Matter

Data sources in ETL platforms fall broadly into two categories.

**Enterprise and private data** lives in organization-owned databases — RDBMS (PostgreSQL, MySQL, Oracle, SQL Server) and NoSQL stores (MongoDB, Cassandra, DynamoDB). These are the backbone of ETL. Most internal business pipelines — sales, operations, finance, product analytics — start here. DataFuseAI already covers this category well.

**Public and external data** comes from two primary channels: static files and APIs. Static files — CSV, Excel, JSON — are snapshots, often sourced from platforms like Kaggle or government data portals. APIs, on the other hand, are live, paginated, and authenticated interfaces through which organizations expose their data to the outside world. NASA publishes astronomy data through APIs. Weather services publish real-time and historical meteorological data through APIs. Financial data providers, government agencies, research institutions, and SaaS platforms — all of them use APIs as the standard mechanism for external data distribution.

This standalone API data is valuable in two ways. First, it can be ingested, transformed, and loaded into a data warehouse directly — as its own source of analytical insight. Second, it can be used to enrich existing RDBMS or NoSQL records by merging in new columns and dimensions that an organization's private databases do not contain. A customer table can be enriched with weather data by city. A product table can be enriched with financial indices by region. These enrichments are only possible when APIs are a first-class data source.

## What We Built — POC Scope

The POC demonstrates end-to-end API connector capability across the following dimensions:

**Authentication types supported:**

- No Auth — for fully public APIs
- Basic Auth — username and password, Base64-encoded in the Authorization header
- API Key — a static key injected as an HTTP header or query parameter, with configurable key name, delivery method, and optional prefix
- Bearer Token — a pre-obtained token injected as `Authorization: Bearer <token>`
- OAuth 2.0 Client Credentials (OAuth CC) — machine-to-machine token exchange using client ID and secret; token fetched automatically, cached, and refreshed
- OAuth 2.0 Authorization Code (OAuth AC) — user-facing browser consent flow with PKCE, redirect URI handling, and silent token refresh

**Pagination strategies supported:**

- No Pagination — single request, full response
- Limit-Offset — standard `?offset=0&limit=100` pattern, incrementing offset until fewer records than the page size are returned
- Page-Size — page number plus size: `?page=1&size=100`, incrementing page until records returned fall below page size
- Cursor — opaque token extracted from the response body via dot-notation path, passed as a parameter in the next request; stops when cursor is absent or null
- Next URL — the API returns the full URL of the next page in the response body; followed until no next URL is present
- Link Header — the next page URL is embedded in the HTTP `Link` response header following RFC 5988 (`Link: <url>; rel="next"`)

Beyond authentication and pagination, the POC also demonstrates:

- Schema inference: automatic discovery of column names and data types from live API responses
- Connection testing: a 6-step diagnostic that validates a profile from DNS resolution through to response format detection
- Data preview: a live, paginated, field-selected view of what the pipeline will receive
- Credential encryption: Fernet-based encryption at rest for all secrets
- Security hardening: SSRF protection, malicious response rejection, credential-safe logging

## Technical Implementation

### Architecture Derived for DataFuseAI

The Potential Datafuseai architecture dervied from POC is structured as a full-stack implementation — frontend, backend, and data side 

**Frontend**

The frontend is responsible for collecting all configuration needed to connect to and read from an API. This is done through a Connection Profile form, which captures the base URL, authentication type, and the credentials appropriate for that auth type — all dynamically rendered based on the selected auth type. The form also collects optional settings such as SSL verification, request timeout, and default request headers.

Beneath each Connection Profile, the user defines one or more Endpoints. An endpoint represents a specific path within the API — for example, `/users` or `/posts` — and is the equivalent of a table in an RDBMS source. Each endpoint is configured independently with its HTTP method, query parameters, path variables, request body (for POST), and pagination strategy. Pagination is set up as extra parameters per endpoint, allowing different endpoints within the same profile to use different pagination conventions.

In the main DataFuseAI platform, Connection Profiles and their Endpoints would be integrated as source nodes within the query builder and pipeline editor, in the same way RDBMS connections and tables appear today.

**Backend**

The backend handles three principal responsibilities.

The first is credential security. All secrets — API keys, passwords, OAuth tokens, bearer tokens — are encrypted at rest using Fernet (AES-256-CBC + HMAC-SHA256). A single call-site encryption pattern ensures that only the EncryptionService can encrypt or decrypt credentials. Credentials are never returned in API responses, never written to logs, and never stored in plaintext. Only a summary (indicating which fields are set, not their values) is surfaced to the frontend.

The second is schema inference. Because each API returns a different response structure, the backend includes an inference engine that recursively walks all records in an API response, accumulates value samples per field path, calculates null percentage across records, and determines the most accurate data type for each path. The engine handles nested JSON (flattened to dot-notation: `customer.address.city`), arrays of objects, arrays of primitives, and correctly distinguishes between booleans and integers — a common edge case in Python where `isinstance(True, int)` evaluates to `True`. The result is a set of schema fields that describe the API's data structure, which the user can then review, include or exclude, alias for display, and optionally override.

The third is handling of malicious or unexpected API responses. Responses that are not valid JSON are rejected at the pagination engine boundary before any data enters the pipeline. Binary formats — executables, compiled files — never reach disk. Hard limits on page count (default 100) and total records (default 10,000) prevent runaway pagination regardless of strategy. SSRF protection blocks requests to RFC 1918 private IP ranges, loopback addresses, and link-local addresses, preventing the connector from being used to scan internal networks.

**Data Side**

At pipeline run time, the data side receives encrypted credentials from the backend, decrypts them in memory for the duration of the request, and uses them to authenticate API calls. The pagination engine — implemented as a Python generator — fetches pages sequentially, yielding one page at a time. This generator pattern allows early exit without fetching unnecessary pages, and enforces safety limits regardless of the API's own behavior. Across all pages, records are accumulated and passed to the transformation and loading stages, which are identical to the existing RDBMS pipeline path. To the rest of the pipeline, an API endpoint is simply another table.

Data side may opt to use pyspark or standard python library for this, according to feasiblity.

## Framework

### Building the Right Product — Clear Understanding of Business Usefulness

The most important question before building any feature is whether it delivers real business value at a cost proportional to its complexity.

The majority of API connector usage in ETL contexts comes from public data sources — weather APIs, government data portals, financial data feeds, research APIs, geolocation services. These sources use simple, well-standardized authentication methods: No Auth, API Key, Basic Auth, or Bearer Token. They require no special setup from the user beyond a URL and a credential value.

OAuth Client Credentials and OAuth Authorization Code flows, by contrast, are primarily used to access private organizational data — for example, connecting to a user's personal Spotify account to retrieve listening history, or to a company's internal Salesforce instance. While this data is not without value, the implementation complexity is significantly higher: each OAuth provider defines its own parameter names, token endpoint requirements, scope formats, and error handling behavior. From the user's perspective, setting up OAuth requires registering an application with the provider, configuring redirect URIs, managing client secrets, and in the case of Authorization Code, completing a browser-based consent flow that is different for every provider. This complexity does not scale well across a general-purpose ETL platform.

The decision was to focus on the four authentication methods that cover the widest range of practical use cases with the lowest configuration burden. This is building the right product — not maximizing feature count, but maximizing value per unit of complexity.

### Building the Product Right — Clear Understanding of Technical Feasibility, Limitations, Best Practices, and Usability

Once the scope is defined, the question becomes whether the implementation is technically sound.

**Handling the variety of API responses.** No two APIs return identical structures. Responses can be flat objects, deeply nested JSON, array-wrapped collections, or a mixture of types in the same field across different records. A schema inference engine that handles only the happy path will produce incorrect column definitions for real-world APIs. The implementation must handle all common structural patterns correctly, distinguish between type-incompatible values in the same field (marking them as "mixed"), and give users the ability to review and override inferred types when the inference is ambiguous.

**Ensuring complete data collection through pagination.** Fetching only the first page of a paginated API and stopping is a silent data loss bug. It produces no error, no warning, and no visible indication that data is missing. Supporting only one pagination strategy is equivalent — any API that uses a different convention will silently return incomplete data. All six industry-standard pagination strategies must be supported, and safety limits must be enforced to prevent infinite loops regardless of the API's behavior.

**Defending against malicious responses.** An API connector makes outbound HTTP requests to external servers. The response is untrusted. A response body containing a binary executable, a compiled script, or a malformed encoding must be identified and rejected before it is processed or persisted. Response size must be capped. SSRF attacks — where a crafted URL causes the server to make requests to internal network resources — must be blocked at the request layer. These are not edge cases; they are expected threat vectors for any system that makes configurable outbound network calls.

## Decisions

### Included

| Decision                                                                      | Rationale                                                                                                                                                                                           |
| ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No Auth, API Key, Basic Auth, Bearer Token                                    | Covers the overwhelming majority of public and partner APIs. Low configuration burden. No external service dependencies.                                                                            |
| All 6 pagination strategies                                                   | Partial support is a silent data correctness bug. Every strategy that exists in the wild must be handled.                                                                                           |
| Schema inference (14 type categories, null tracking, dot-notation flattening) | Users must understand the shape of data before loading it. Manual column definition for arbitrary API responses is not practical.                                                                   |
| Cumulative paginated data collection via GET and POST                         | Both HTTP methods are used by real APIs for data retrieval. POST is used when query parameters would exceed URL length limits or when the API requires a request body to specify filters.           |
| Connection testing (6-step diagnostic)                                        | Most connection failures are configuration errors. A diagnostic that pinpoints the failure step — DNS, network, authentication, HTTP response, format, sample — saves significant debugging time. |
| Encryption at rest (Fernet AES-256-CBC + HMAC-SHA256)                         | Storing credentials in plaintext is a critical security failure. Encryption is a non-negotiable baseline requirement.                                                                               |
| SSRF protection                                                               | In any shared or cloud deployment, an unprotected configurable HTTP client is a network enumeration vector. RFC 1918 blocking is required before production deployment.                             |
| Malicious response handling                                                   | Responses from external APIs are untrusted. Binary content must be rejected. Runaway pagination must be halted by hard limits.                                                                      |

### Excluded

| Decision                            | Rationale                                                                                                                                                                                                                                                                                                                                           |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OAuth Client Credentials (OAuth CC) | Primarily used for organizational-internal integrations. Each provider defines different parameter names, scope formats, and token endpoint behaviors. Implementation complexity is high relative to the breadth of practical use cases covered.                                                                                                    |
| OAuth Authorization Code (OAuth AC) | Requires browser-based user consent, provider-specific OAuth app registration, redirect URI configuration, PKCE/state management, and a token refresh lifecycle. The user experience adds significant configuration overhead per provider, making it a poor fit for a general-purpose ETL source connector at this stage.                           |
| POST / Write operations to APIs     | Loading data into a third-party API via POST is a fundamentally different capability — it transforms the connector from a data source into a data destination. This doubles the scope, introduces new concerns around idempotency, partial write failures, and error recovery, and is outside the purpose of a read-oriented ETL source connector. |

These exclusions are deliberate and revisable. As business requirements evolve and the complexity-to-value ratio shifts, any of them can be added in a future iteration.
